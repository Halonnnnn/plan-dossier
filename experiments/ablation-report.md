## 2. Research Questions and Hypotheses

Core question: when loaded alone, does plan-dossier deliver a measurable net benefit over the bare baseline?

| Hypothesis | Content | Decision rule (locked before runs) |
|---|---|---|
| H1 | On T1 (cross-phase task), A1 pass count ≥ A0 and the median search-to-first-edit is lower | Holds: both conditions met and A1 leads in ≥ 2/3 of paired comparisons; reversed direction rules it out; mixed results yield no conclusion |
| H2 | On T2 (small task), A1 degrades correctly (plain text / minimal, no full-form artifacts) with token overhead ≤ +20% relative to A0 | Holds: both conditions met; any full-form artifact rules it out |

No hypothesis is pre-registered for ledger accuracy: it is an observational item (a known weakness) — reported, never judged.

## 3. Experimental Design

### 3.1 Independent Variable

The only variable: skill loading.

| Arm | Loaded | Note |
|---|---|---|
| A0 | No skills at all | Bare baseline |
| A1 | plan-dossier only | Single-variable test of plan-dossier |

### 3.2 Frozen Controlled Variables

The following are byte-identical or configuration-identical across all runs; any deviation voids the run:

- SDD document (verbatim) and initial prompt (verbatim)
- Initial repo snapshot (same commit)
- Project-level conventions (AGENTS.md or equivalent, verbatim)
- Model versions, permission mode, thinking level
- A fresh workspace directory per run: no project memory, no prior sessions, no `.plan-dossier/` residue
- No human intervention throughout: no answering questions mid-run, no course corrections

### 3.3 Tasks

| Task | Form | Selection criteria | Status |
|---|---|---|---|
| T1 | Plan and execute in separate sessions; large enough to trigger full form | A real cross-module change with known pain; multiple files, dependency ordering, several directions excluded at planning time | TBD (fill in SDD path and acceptance script path) |
| T2 | Completed in a single session | Single-file small feature; ideal outcome is plan-dossier judging plain text on its own | TBD (same) |

### 3.4 Run Matrix and Execution Order

2 arms × 2 tasks × 3 repetitions = 12 runs. The order was generated by shuffling with seed 20261120 and is executed in sequence; runs of the same arm must not be batched:

| # | Run | # | Run |
|---|---|---|---|
| 1 | T1-A0-r3 | 7 | T1-A1-r3 |
| 2 | T2-A1-r3 | 8 | T1-A1-r2 |
| 3 | T1-A0-r1 | 9 | T2-A0-r1 |
| 4 | T1-A1-r1 | 10 | T2-A0-r3 |
| 5 | T2-A1-r2 | 11 | T2-A1-r1 |
| 6 | T1-A0-r2 | 12 | T2-A0-r2 |

Workspace naming: `runs/{task}-{arm}-r{n}/`; each workspace is sealed after its run and never reused.

Budget-permitting upgrade (does not change the analysis): raise T1 to 5 repetitions per arm, then reshuffle the whole order (seed 20261121).

## 4. Per-Run Protocol

1. Copy the frozen snapshot into a fresh workspace directory
2. New session: enter the task's fixed initial prompt and complete planning (T1 ends at artifact freeze; T2 finishes in one session)
3. T1: open a new session and execute against the artifacts; the A0 control likewise splits into two sessions, the second given only the SDD
4. Run the acceptance assertion script (a fixed script per task, behavioral assertions)
5. Archive: session transcript (JSONL), `.plan-dossier/` artifacts (if any), final diff, acceptance script output, token/wall-time report
6. Seal the workspace
7. Record mid-run failures as-is: no retry, no workaround (failure is data)

## 5. Operational Metric Definitions

| Metric | Definition | Data source | Applies to |
|---|---|---|---|
| Task passes | Runs whose acceptance assertion script passes (binary) | Script output | Both arms |
| Search-to-first-edit | Count of exploratory tool calls (Grep/Glob/Read etc.) before the first Edit/Write in the execution phase | Transcript | Both arms |
| Reuse ratio | Share of task-card cites actually consumed during execution (consumed = ledger entry consulted and target region accessed via its locator) | Transcript + artifacts | A1 only |
| Misuse-after-staleness | Edits to regions pointed at by stale entries (hash mismatch or declared invalidation) without re-reading first / total stale hits | Transcript + artifacts | A1 only |
| Tokens / wall time | Per-run totals | Harness report | Both arms |
| Ledger accuracy | Share of resolvable cites (ID exists; locator path and span valid at freeze time) | Artifacts, blind scoring | A1 only |

Blind-scoring procedure: scorers never see run directory names or arm labels; materials are anonymized with sequential IDs before scoring.

## 6. Statistical Convention

- n=3 supports directional conclusions only: report per-cell medians plus all data points; no significance testing
- Pairing is aligned by (task, rep): T1-A1-r1 against T1-A0-r1
- Conclusion vocabulary is limited to three values: holds / does not hold / no conclusion

## 8. Validity Threats and Limitations (upper bound on interpretation)

- n=3 is directional evidence; it cannot support any "significant" claim
- There is only one task pair (T1/T2); conclusions do not generalize to other task types
- The A1−A0 gap includes the token cost of the skill prompt itself — part of the "net effect" by definition, but attribution narratives must state this
- Acceptance assertions are authored by the experiment designer; faulty assertions hit both arms equally, but can wrongly fail both
- Model-version drift is mitigated by the single time window; if the window spans days, record it in 7.4
