# Plan Dossier

把规划阶段的投入沉淀为按失效方式划分的四层工件：计划冻结、账本只追加、交接记录动态追加。执行方按引用精确定位、按需读取，不重新搜索；审查方拿到隔离视图，不被前序结论带偏。

## 职责与边界

Plan Dossier 是规划与工件编写 skill，不是执行编排框架。它产出完整、准确、一致、可直接交接的规划工件；下游 agent 按各自的工作流消费。

本 skill 定义：

- 规划方法与工件结构（L0–L3、views、packet）。
- 规划数据的语义与关系：任务状态与依赖、排除项、信任分级、失效、替代。
- 任务分解、约束、验收标准。
- 交接产物的内容与质量要求：缺三段的 handoff 不是合法 handoff；缺四项内容的 review packet 不是合法 review packet。

本 skill 不规定：

- 下游如何执行任务、应对偏离与失败：工具调用顺序、编辑操作、执行编排。
- 工件如何被消费：读取顺序、校验时机、恢复流程。
- 审查方的行为与审查流程。

执行期写入的工件，责任划分如下：

| 工件 | Plan Dossier 定义 | 下游 agent 决定 |
|---|---|---|
| `dag[].status` | 状态含义；断点续传语义 | 是否更新、何时更新 |
| handoff/*.md | 三段结构与字段语义 | 何时生成、何时写入 |
| Deviations | 偏离记录的含义与内容 | 实际记录什么 |
| State Snapshot | 快照必须表达什么 | 何时更新、何时消费 |

resume 是可选项：工件提供断点，不保证下游维护。删除执行处方不删除任何数据完整性要求，只是把"何时、由谁"交给下游。

## 形态选择

触发后按任务特征判定形态（完整 / 最简 / 纯文本），用一句话说明判定结果与理由后直接开工，判断一目了然时不要让用户再确认一遍。完整形态条件均不满足且任务较小时，默认纯文本，落盘工件不是强制要求。仅在任务范围确实不明确时提问（例如既可能是完整形态也可能是纯文本，或涉及 schema、安全边界等敏感改动）。用户指令已明确形态（如"出完整 plan""简单列个计划"）时直接照办，不重复问。

**完整形态**（四层齐全 + views），满足以下任一特征时推荐：

- 规划与执行由不同模型、不同会话或不同角色完成，执行方需要知道"代码在哪、哪些不用看"。
- 多个执行器并行或分批执行同一计划的不同部分，每个执行器只加载与自己相关的上下文。
- 任务长到必然发生上下文压缩，压缩后需要回到精确的源码内容。
- 审查环节需要独立判断执行结果。
- 规划阶段排除过若干方案，执行方若不知道排除理由，很可能自行回退。

**最简形态**（单节点、无交接、不会跨越上下文压缩的小计划）：

- plan.yaml（单节点 dag）+ 一张任务卡 + ledger.jsonl（可为空文件），不建 handoff/。
- 简化只减文件数，不减校验规则：cites 引用制、信任分级、excluded、gaps 必填照常生效。

**纯文本计划**（不落 `.plan-dossier/`，直接回应用户）：

- 纯调研且产出本身就是一份文档、没有后续执行阶段。
- 用户只要一份轻量计划。此时说明本 skill 的适用边界，按用户要求输出。

`views/plan.view.md` 的渲染跟随形态默认值：完整形态默认渲染（人类审批与独立审查需要），最简形态默认不渲染、审批直接看 plan.yaml 内容。渲染与否在形态判定的同一句话中说明，用户可在规划开始前后随时改变默认。`review.packet.md` 不受此影响，交接审查时按需编译。

## 核心原则

1. **按失效方式分工件，不按主题。** 源码定位只会过期，检索结论可能出错，计划条款需要人判断。三类内容的校验方式和责任边界不同，不能混放在一个文件里。
2. **以获取成本为记录标准。** 一条账本条目的价值约等于"重新获取的成本 × 预计复用次数"。经过多次搜索才定位的结果、排除掉的模块，值得记录；已知路径直接打开，不记录。
3. **默认重新获取，不默认复用。** 哈希（或目视）完全一致才复用，任何不一致都重读。错误结论导致返工的代价通常是重读代价的 100 倍以上，保守策略的期望损失更低。
4. **按角色裁剪交接内容。** 执行方需要结论、排除项和精确定位；审查方只需要原始需求、变更差异和修改前后的完整文件，不能拿到规划结论。
5. **单一事实源 + 渲染视图。** 机器读 plan.yaml 与任务卡，人读由它们渲染的视图。不手工维护两份等价文档；同一数据清单在 L0 与全部任务卡中也只在一处展开，他处用锚点或 ID 引用。

## 目录结构

全部位于 `.plan-dossier/` 下。每层对应一种失效方式，据此确定变更规则和校验手段：

| 层 | 文件 | 读取方 | 变更规则 | 校验方式 |
|---|---|---|---|---|
| L0 | plan.yaml | 所有角色常驻 | 冻结，修改即升版本归档 | 人工判断 + schema 检查 |
| L1 | tasks/NN_*.yaml | 仅对应执行器 | 随 L0 一起冻结 | cites 引用存在性检查 |
| L2 | ledger.jsonl | 规划/执行按需 | 只追加，修订用 supersedes | region_sha 惰性比对（可选） |
| L3 | handoff/NN_to_MM.md | 下游执行器 | 每完成一步追加 | 以最新一份为准 |
| views | plan.view.md、review.packet.md | 人类/审查 | 随时重建 | 派生物，无需校验 |

## 工件规范

### L0 plan.yaml

```yaml
task_id: refactor-payment
version: 1
base: {repo: "acme/api", commit: "abc123", env: ["运行测试前需 source env.local.sh", "基线编译存在 1 个与本次无关的既有失败"]}
objective: "把所有支付校验收敛到 PaymentValidator"

constraints:
  - id: c1
    text: "不要修改 billing 层的分层结构"
    why: "上游按层路由，改层会让 A/B 分流失效"
    trust: unverified
    by: {model: "planner-a", run: "r17", at: "2026-11-19T10:00:00+08:00"}
    rederive_cost: high
  - id: c2
    text: "PaymentService.validate 的公开签名不得变"
    trust: checked
    assertion: {replay: "grep -rn 'def validate' src/payment/", expects: "仅 PaymentService.validate 一处"}

acceptance:
  - "所有下单路径都经过 PaymentValidator"
  - "现有 payment 测试全绿"

dag:
  - {id: s1, task: "tasks/01_extract_validator.yaml", depends_on: [], status: pending}
  - {id: s2, task: "tasks/02_replace_callers.yaml", depends_on: [s1], status: pending}

risks:
  - {id: r1, text: "校验收敛后 RefundService 旁路绕过校验", mitigated_by: ["s2.1"]}

decisions:
  - id: d1
    text: "用组合而非继承"
    why: "避免 PaymentService 的构造参数扩散"
    trust: unverified
    by: {model: "planner-a", run: "r17", at: "2026-11-19T10:05:00+08:00"}

gaps:  # 计划明确未覆盖的判断维度，执行方在这些维度自行判断
  - "金额为零的边界输入分支未逐用例推导"

open_questions:
  - "退款路径是否也算校验入口（未确认）"

excluded:
  - {locator: "src/billing.py", reason: "支付校验不在 billing 层"}
  - {locator: "src/legacy/**", reason: "已废弃，不参与调用链"}
```

编写规则：

- 全文控制在 2K tokens 以内。任务细节已移入 L1，超预算说明有内容应下沉到 ledger 或任务卡。
- `excluded` 与 `gaps` 在计划冻结时必须存在，可为 `[]`，不得省略字段。`excluded` 为空时在 `open_questions` 注明"未做排除"；`gaps` 是规划方对"哪些判断维度明确没做"的显式回答，空列表表示已知维度均已覆盖。
- `gaps` 与 `open_questions` 语义不同：gaps 是已知未覆盖、无需回答的维度；open_questions 是待回答、待裁决的问题。两者不得混放。
- `risks[].mitigated_by` 非空，锚点格式：`aN` 指向 L0 acceptance 第 N 条，`sM.N` 指向任务卡 M 的 acceptance 第 N 条。给不出锚点的风险不是"已设防"，降级写进 `open_questions` 并注明。
- `base.env` 记录执行方不带上就会浪费试错的环境事实（构建前置命令、基线既有失败等），与 commit 同属任务基线。ledger 的 locator 是 path+span，装不下环境事实，且账本目录在 packet 中可被截断，所以放 base 常驻。条目过期（如基线被修复）时，变化经 handoff 的 State Snapshot 传递，不改冻结的 L0。
- `dag[].status` 只有五个取值：`pending`、`in_progress`、`done`、`blocked`、`needs_review`。status 是断点续传入口——执行状态只存在这个字段里，不存在于文字描述。含义由本 skill 定义；是否更新、何时更新由下游 agent 决定，更新不算修改计划，不升 version。
- `needs_review` 由规划方在升版本时写入，标记结果产生于旧版本计划的节点。它不给执行方新增任何规则：按既有 DAG 语义，非 `done` 即下游依赖未满足，恢复走既有的升版本重审流程（规划方重写并重新冻结）。变更未触及的节点保持原状态，不自动回滚。
- `trust: checked` 必须带 `assertion`，`replay` 是一条可原样执行的命令或明确的符号查找，规划方标注 checked 前必须实际执行过一次，未执行过只能标 unverified；`trust: unverified` 必须带 `by`（来源）和 `rederive_cost`（low/medium/high），使用前交叉核对。
- 冻结后文件字节不再变化。需要改计划时 `version` 加一，旧版本归档为 `plan.v1.yaml`。冻结部分的字节稳定，可长期命中前缀缓存。
- 防回退的一行式排除项放 `excluded`；详细踩坑过程放 ledger（`verdict: excluded` 的条目）。L0 不承载长篇记录。
- `excluded` 是计划的范围约束：对排除项的修改构成计划失效事件。事件可记录（Deviations）、影响可评估（触及哪些决策与任务）；需要修订时走升版本。局部失效不自动作废计划的其余部分。下游如何响应该事件是它自己的工作流。

### L1 任务卡

```yaml
id: s1
action: "抽出校验逻辑到新模块"
depends_on: []
cites: ["L-0042", "L-0017"]
outputs: ["src/payment/validator.py"]
acceptance:
  - "PaymentValidator 覆盖全部 5 处校验规则"
```

编写规则：

- 一张卡一个 DAG 节点，文件名 `NN_动作简名.yaml`，NN 与 `dag[].id` 的序号一致。
- 单卡控制在 1K tokens 以内。超出说明卡内混入了其他节点的内容或账本细节。
- `cites` 只引用 ledger.jsonl 中已存在的条目 ID，不复制条目内容，更不抄源码原文。执行方凭 ID 去账本查定位，再按定位读源码。
- `acceptance` 是本节点的可验证断言，与 L0 的全局验收互补，不得为空。
- 任务卡随 L0 一起冻结。执行中发现步骤有误属于计划偏离：记入 handoff 的 Deviations，经升版本解决，不原地改卡。

### L2 ledger.jsonl

只追加，每行一条：

```jsonc
{"id": "L-0042", "locator": {"path": "src/payment.py", "span": [20, 45]}, "verdict": "relevant", "intent": "定位支付校验入口", "cost": {"tool_calls": 12, "tokens": 4800}, "by": {"model": "planner-a", "run": "r17", "at": "2026-11-19T10:02:00+08:00"}, "supersedes": null, "region_sha": "sha256:44ae...", "invalidation": ["PaymentService.validate 签名变化", "src/payment.py 被移动或改名"]}
```

记录始终是自主裁量，按搜索成本（而非读取成本）衡量的重新获取成本判断：只有当条目价值（重新获取成本 × 预计复用次数）明显超过记录成本时才写入，账本为空或稀疏都可接受，不为合规而记录：

| 场景 | 记录 | 原因 |
|---|---|---|
| 已知路径，直接打开文件 | 否 | 重新打开只需数百 tokens |
| 经过多次 grep，排除大量候选后定位 | 是 | 重新获取等于再搜索一遍 |
| 排除了某个模块或目录 | 是 | 一行记录避免一次大范围探索 |
| 大文件的局部阅读 | 是 | 重新读取需要重新定位 |

字段规则：

- `verdict` 只取 `relevant`、`excluded`、`unknown` 之一。
- 修订旧结论时追加新行并在 `supersedes` 写入被替代条目的 ID，不修改原行。
- `region_sha` 可选。有运行时支持时自动计算；没有时省略——不带哈希的条目没有完整性保证，本身不足以作为编辑依据，编辑时需读取目标片段。
- `invalidation` 可选，规划阶段写入：声明式失效条件，写明在什么情况下本条结论不再成立（如"被引用符号的签名变化""被引用文件被移动"）。它是规划侧元数据，为既有的上下文失效流程提供显式触发依据；不给下游阶段新增任何义务——执行方加载片段时走的失效流程与从前完全一致。写不出具体条件时省略；模糊条件（"代码变了"）比不写更糟。
- 账本不存源码内容：存下的内容会静默过期，且没有检测手段。账本只存定位与结论，需要时按定位读取源码。

### L3 handoff/NN_to_MM.md

上游执行器完成后写入，文件名按任务卡 ID：`01_to_02.md`。三段齐全，缺一不可：

```markdown
# s1 → s2

## Actual Outputs
- src/payment/validator.py（新建，5 处校验规则）

## Deviations
- 计划说 3 处调用点，实际 4 处，第 4 处在 RefundService

## State Snapshot
- L-0042 已过期（src/payment.py 在 s1 中被修改），s2 前需重读
- 新符号 PaymentValidator 已可被 s2 直接引用
```

- `Actual Outputs`：实际产生或修改的文件路径与摘要。
- `Deviations`：相对计划的偏离、新发现、临时妥协。没有偏离时写"无"。
- `State Snapshot`：下游启动前必须注意的事项，包括哪些账本条目已因本次修改过期。

### views/（编译产物）

- `plan.view.md`：由 plan.yaml + tasks/ 渲染的人类审阅视图，包含目标、约束、DAG 表、每卡摘要、排除项。交付用户审批时给这份，不给裸 YAML。
- `review.packet.md`：审查隔离视图，内容只有四项——原始需求、变更差异、变更文件修改前后的完整内容、验收标准。由交接时编译生成，不手工编辑，不包含 plan.yaml、任务卡、excluded、账本、handoff。
- views/ 整个目录可删除可重建，冲突时以 L0-L3 为准。

## 工作流

### 规划阶段

1. **明确边界。** 确定三件事：最终可验证的产出；全局不可违背的硬约束；子任务依赖与可并行集合。说不清楚就先向用户确认，不带模糊目标进入下一步。
2. **边探索边记账。** 每次昂贵的搜索结束后按记录标准表追加 ledger 条目。规划结束时账本应已就位，任务卡的 cites 才有东西可引。
3. **写 L0 plan.yaml。** 按 schema 编写，遵守 2K 预算与 excluded 必填规则。
4. **写 L1 任务卡。** 每个 DAG 节点一张卡，cites 指向账本条目。
5. **冻结并渲染。** 检查通过后冻结 L0 与 L1；用户选择渲染时生成 views/plan.view.md 交用户审批，未选择渲染时审批对象是 plan.yaml 与任务卡内容。审批不通过则升版本重写，不原地改冻结件。

### 交接（packet 组装）

交接给执行方或规划方时，按以下顺序组装：

```text
packet = 系统提示 + plan.yaml + 账本目录 + 当前任务卡 + 上游 handoff
```

- 稳定内容在前（plan.yaml、账本目录），易变内容在后（当前任务卡、handoff、按需片段）。顺序即 prompt 拼装顺序，稳定前缀可命中缓存。
- 总预算不超过 4K tokens。超出时截断优先级：先截账本目录，再截 open_questions；`excluded`、`constraints`、`risks`、`gaps` 不截。
- packet 不含 views。
- packet 不含源码内容；片段按步骤在 packet 之外加载。
- 账本目录每行：条目 ID、路径与行范围、verdict、成本、一句话目的。不含哈希。
- 目录末尾列出未选入的条目数量和估算体量。使用方必须知道信息不完整，否则只能在全部重读和直接采信之间二选一。

各角色的可见内容：

| | plan.yaml | 任务卡 | 账本目录 | excluded | 源码片段 | unverified 结论 |
|---|---|---|---|---|---|---|
| 规划 | 全量 | 全量 | 目录 + 按需 | 全量 | 按需 | 全量 |
| 执行 | 全量 | 仅自己的卡 | 目录 + 按需 | 全量 | 按需 | 全量 |
| 审查 | 不提供 | 不提供 | 不提供 | 不提供 | 变更文件前后全文 | 不提供 |

### 执行阶段

执行行为属于下游 agent 自己的工作流，本规范不做任何规定。工件提供的是：

- plan.yaml、账本目录与所属任务卡让执行方无需重新检索即可获得结论、排除项和精确定位；其他任务卡不在其 packet 内（靠组装隔离，不靠规则禁止）。
- 账本 locator 是指针不是内容：cites 的消费方式就是读取目标片段。哈希不匹配的条目不足以作为编辑依据。
- `excluded` 与冻结的任务卡让偏离可检测：越界修改或违背冻结步骤即计划失效事件，Deviations 是其记录通道。
- `dag[].status` 是唯一权威的执行状态——断点续传入口。
- `trust: checked` 的 assertion 可重放，任何结论都能以一条命令的成本重新验证。

### 审查阶段

review.packet.md 在交接时编译（见 views/），隔离是其内容的属性，不是加给审查方的规则。审查方如何工作是下游自己的流程；handoff 只能作为查找线索，不能作为结论依据。

## 失效处理

每级失效的含义，以及工件为其提供的支持：

| 级别 | 含义 | 工件支持 |
|---|---|---|
| 位置失效 | 被引用文件被删除或移动——条目按定义即作废 | 重新检索的结果记录为新条目 |
| 内容失效 | region_sha 不匹配，或目视内容与 intent 不符 | 修订记录为带 `supersedes` 的新条目；handoff 的 State Snapshot 是向下游传递的通道 |
| 上下文失效 | 内容未变但调用方或依赖已变，或条目声明的 `invalidation` 条件已成立 | 有 assertion 时，重放一条命令即可重新验证；没有则该结论在重新验证前按 unverified 对待 |

- 文件变化只影响指向它的条目，计划与账本的其余部分仍然有效。局部失效或局部计划失效事件不作废整份计划。
- 下游何时、如何执行这些检查是它的工作流；工件的职责是让每次检查便宜、结果可记录。第三级失效没有低成本的通用检测手段——assertion 与声明的 `invalidation` 条件是部分答案。

## 验证清单

交付 `.plan-dossier/` 前逐项执行，任何一项不满足先修正再交付：

1. 引用完整性：扫描全部任务卡的 `cites` 后，每个 ID 都能在 ledger.jsonl 中找到对应行；`dag[].task` 指向的文件都存在；解析全部 `risks[].mitigated_by` 锚点（`aN`、`sM.N`），每个都能在 L0 acceptance 或对应任务卡中找到条目。
2. 信任分级完备：`trust: checked` 的条目全部带 `assertion`；`trust: unverified` 的条目全部带 `by` 和 `rederive_cost`。
3. `excluded` 与 `gaps` 字段存在；为空时是 `[]`，`excluded` 为空需在 `open_questions` 注明原因。
4. 预算达标：plan.yaml 估算不超过 2K tokens；每张任务卡不超过 1K；packet 不超过 4K 且末尾有未选入条目清单。
5. 职责分离：plan.yaml 中没有检索过程细节（那是账本的职责），没有源码原文摘录；任务卡中没有抄写账目内容或源码。
6. 审查隔离：review.packet.md 中检索不到 plan.yaml 的 objective 原文、excluded 条目、账本 ID。
7. 渲染一致：views/plan.view.md 由当前冻结版本的 L0 + L1 渲染，DAG 状态与 plan.yaml 一致。
8. 执行留痕（执行后诊断项，不是规划交付门槛）：done 状态的任务卡应有完整的 handoff 文件。缺失说明下游未维护，报告即可，不阻塞计划交付。
9. 单一来源（目视检查，无法机械化）：L0 与全部任务卡中，同一数据清单（键列表、白名单、枚举）只在一处展开，其余位置均为锚点或 ID 引用。

## 常见错误

只列上方规则没有点名的失效模式：

- **把 L0 写成散文长文档。** 每个角色每次交接都重复付费，且大部分内容与当前角色无关。
- **省略排除项。** 只写"怎么做"不写"为什么不那样做"，是执行方遇到阻力就擅自回退的头号原因。
- **用复选框代替 handoff。** 断点续传需要实际产物路径和偏离记录，`[x]` 无法让新会话接续上下文。
- **向审查方提供计划或排除项。** 破坏审查独立性；排除项还会诱导审查回避某些区域。

## 降级与运行时支持

本 skill 是文件规范，无任何工具支持即可运行：账本由 agent 按记录标准手动追加；无 region_sha 的条目在使用时读取目标片段；校验退化为"目视比对 + 不符即走失效流程"。

有运行时支持（hook 或 MCP 工具）时可自动化两件事，均不改变文件格式：

- 在 read、grep、glob 调用时自动生成账本条目并计算 region_sha；
- 片段加载时自动做 region_sha 惰性校验，失效时提示重新获取；进一步可加内容缓存（按哈希去重的 blob 存储），属于工具层实现，不在本规范内。

## 效果评估

评估要同时报告四项：重复获取比例、搜索到首次编辑的工具调用次数、任务通过率、失效后的错误使用率。只报告单一指标会被误导——全部作废也能让"失效识别率"达到 100%。

本 skill 有一条可证伪预测：排除项带来的收益应大于片段复用带来的收益。实测相反则说明执行方缺的主要是内容而非定位信息，应优先加强内容侧支持。
