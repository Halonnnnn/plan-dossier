# 工作流与失效规则

各阶段工作流（规划、交接组装、执行、审查）、冻结与升版本规则、失效处理。执行任一阶段、组装 packet 或处理失效条目时加载本文件。工件结构见 [schema.md](schema.md)。

## 规划阶段

1. **明确边界。** 确定三件事：最终可验证的产出；全局不可违背的硬约束；子任务依赖与可并行集合。说不清楚就先向用户确认，不带模糊目标进入下一步。
2. **边探索边记账。** 每次昂贵的搜索结束后按记录标准表追加 ledger 条目。规划结束时账本应已就位，任务卡的 cites 才有东西可引。
3. **写 L0 plan.yaml。** 按 schema 编写，遵守 2K 预算与 excluded 必填规则。
4. **写 L1 任务卡。** 每个 DAG 节点一张卡，cites 指向账本条目。
5. **冻结并渲染。** 检查通过后冻结 L0 与 L1；用户选择渲染时生成 views/plan.view.md 交用户审批，未选择渲染时审批对象是 plan.yaml 与任务卡内容。审批不通过则升版本重写，不原地改冻结件。

## 冻结与升版本

- 冻结后 L0 文件字节不再变化。需要改计划时 `version` 加一，旧版本归档为 `plan.v1.yaml`。冻结部分的字节稳定，可长期命中前缀缓存。
- 任务卡随 L0 一起冻结。执行中发现步骤有误属于计划偏离：记入 handoff 的 Deviations，经升版本解决，不原地改卡。
- `dag[].status` 是断点续传入口——执行状态只存在这个字段里，不存在于文字描述。是否更新、何时更新由下游 agent 决定，更新不算修改计划，不升 version。取值集合见 [schema.md](schema.md)。
- `needs_review` 由规划方在升版本时写入，标记结果产生于旧版本计划的节点。它不给执行方新增任何规则：按既有 DAG 语义，非 `done` 即下游依赖未满足，恢复走既有的升版本重审流程（规划方重写并重新冻结）。变更未触及的节点保持原状态，不自动回滚。

## 交接（packet 组装）

交接给执行方或规划方时，按以下顺序组装：

```text
packet = 系统提示 + plan.yaml + 账本目录 + 当前任务卡 + 上游 handoff
```

- 稳定内容在前（plan.yaml、账本目录），易变内容在后（当前任务卡、handoff、按需片段）。顺序即 prompt 拼装顺序，稳定前缀可命中缓存。
- 总预算不超过 4K tokens。超出时截断优先级：先截账本目录，再截 open_questions；`excluded`、`constraints`、`risks`、`gaps` 不截。
- packet 不含 views。
- packet 不含源码内容；片段按步骤在 packet 之外加载。
- 账本目录每行：条目 ID、路径与行范围、verdict、成本、一句话目的。不含哈希。
- 目录末尾列出未选入的条目数量和估算体量。使用方必须知道信息不完整，否则只能在全部重读和直接采信之间二选一。

各角色的可见内容：

| | plan.yaml | 任务卡 | 账本目录 | excluded | 源码片段 | unverified 结论 |
|---|---|---|---|---|---|---|
| 规划 | 全量 | 全量 | 目录 + 按需 | 全量 | 按需 | 全量 |
| 执行 | 全量 | 仅自己的卡 | 目录 + 按需 | 全量 | 按需 | 全量 |
| 审查 | 不提供 | 不提供 | 不提供 | 不提供 | 变更文件前后全文 | 不提供 |

## Handoff 契约（L3）

- handoff/NN_to_MM.md 由上游执行器完成节点后写入，文件名按任务卡 ID（`01_to_02.md`）。
- Actual Outputs、Deviations、State Snapshot 三段齐全，缺任一段即不是合法 handoff。三段结构与示例见 [schema.md](schema.md)。
- 同一节点以最新一份 handoff 为准；它既是偏离的记录通道，也是向下游传递"哪些账本条目已过期"的载体。

## 执行阶段

执行行为属于下游 agent 自己的工作流，本规范不做任何规定。工件提供的是：

- plan.yaml、账本目录与所属任务卡让执行方无需重新检索即可获得结论、排除项和精确定位；其他任务卡不在其 packet 内（靠组装隔离，不靠规则禁止）。
- 账本 locator 是指针不是内容：cites 的消费方式就是读取目标片段。哈希不匹配的条目不足以作为编辑依据。
- `excluded` 与冻结的任务卡让偏离可检测：越界修改或违背冻结步骤即计划失效事件，Deviations 是其记录通道。
- `dag[].status` 是唯一权威的执行状态——断点续传入口。
- `trust: checked` 的 assertion 可重放，任何结论都能以一条命令的成本重新验证。

## 审查阶段

review.packet.md 在交接时编译（见 views/），隔离是其内容的属性，不是加给审查方的规则。审查方如何工作是下游自己的流程；handoff 只能作为查找线索，不能作为结论依据。

## 失效处理

每级失效的含义，以及工件为其提供的支持：

| 级别 | 含义 | 工件支持 |
|---|---|---|
| 位置失效 | 被引用文件被删除或移动——条目按定义即作废 | 重新检索的结果记录为新条目 |
| 内容失效 | region_sha 不匹配，或目视内容与 intent 不符 | 修订记录为带 `supersedes` 的新条目；handoff 的 State Snapshot 是向下游传递的通道 |
| 上下文失效 | 内容未变但调用方或依赖已变，或条目声明的 `invalidation` 条件已成立 | 有 assertion 时，重放一条命令即可重新验证；没有则该结论在重新验证前按 unverified 对待 |

- 文件变化只影响指向它的条目，计划与账本的其余部分仍然有效。局部失效或局部计划失效事件不作废整份计划。
- 下游何时、如何执行这些检查是它的工作流；工件的职责是让每次检查便宜、结果可记录。第三级失效没有低成本的通用检测手段——assertion 与声明的 `invalidation` 条件是部分答案。
