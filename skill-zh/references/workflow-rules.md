# 工作流与失效规则

各阶段工作流（规划、交接组装、执行、审查）、冻结与升版本规则、失效处理。创建或修订 Dossier、编译交接或审查 packet、或处理失效条目时加载本文件。工件结构见 [schema.md](schema.md)。

## 规划阶段

1. **明确边界。** 确定三件事：最终可验证的产出；全局不可违背的硬约束；子任务依赖与可并行集合。说不清楚就先向用户确认，不带模糊目标进入下一步。
2. **边探索边记账。** 每次昂贵的搜索结束后按记录标准表追加 ledger 条目。规划结束时账本应已就位，任务卡的 cites 才有东西可引。
3. **写 L0 plan.yaml。** 按 schema 编写，2K 预算按默认目标对待（超限时报告用户），excluded/gaps 必填规则照常遵守。
4. **写 L1 任务卡。** 每个 DAG 节点一张卡，cites 指向账本条目。
5. **渲染、自检与冻结。** 按需渲染 views/plan.view.md（未选择渲染时审批对象是 plan.yaml 与任务卡内容），对照 checklist 自检通过后冻结 L0 与 L1 交付。审批不通过则升版本重写，不原地改冻结件。

## 冻结与升版本

- 冻结后 L0 文件字节不再变化。需要改计划时 `version` 加一，旧 L0 归档为 `plan.v1.yaml`，被重写的任务卡归档到 `archive/vN/tasks/`（plan.vN 快照自洽的依据；`tasks/` 只保留当前冻结版）。
- 任务卡随 L0 一起冻结。执行中发现步骤有误属于计划偏离。执行方回写 handoff 时，Deviations 是其记录通道，经升版本解决；不回写时，偏离处理归其自身工作流。两条路径下都不得原地改卡。
- 执行进度不进入 dossier。冻结后 plan.yaml 字节不再变化——没有任何运行时回写，稳定前缀得以跨交接、跨模型长期命中缓存。进度、断点续传、重试状态归执行方自己的工作流。
- `dag[].carryover` 仅由规划方在升版本时写入，语义是静态规格继承：该节点的目标、依赖与约束相对上一版本无实质变更，旧结果可能可复用。每个节点规划方二选一：重写，或标 `carryover: true`。以下任一实质变更即禁止标记：节点自身任务卡内容（action、outputs、acceptance）、`depends_on` 集合、任一上游依赖节点 outputs/接口契约（上游重写但 outputs 契约不变时仍可标记）、节点 cites 指向的账本结论、plan 级 `constraints` 变化波及该节点。旧结果是否实际复用，由执行方对照自己维护的进度判断；不自动回滚。

## 交接（packet 组装）

交接给执行方或规划方时，按以下顺序组装：

```text
packet = 系统提示 + plan.yaml + 账本目录 + 当前任务卡 + 上游 handoff
```

- 稳定内容在前（plan.yaml、账本目录），易变内容在后（当前任务卡、handoff、按需片段）。顺序即 prompt 拼装顺序，稳定前缀可命中缓存。
- 总预算不超过 4K tokens。超出时截断优先级：先截账本目录，再截 open_questions；`excluded`、`constraints`、`risks`、`gaps` 不截。截断只发生在组装视图内、不改原文件；open_questions 位于 plan.yaml 尾部，截它对前缀缓存的失效面最小。
- packet 不含 views。
- packet 不含源码内容；片段按步骤在 packet 之外加载。
- 账本目录每行：条目 ID、路径与行范围、verdict、成本、一句话目的。不含哈希。
- 目录末尾列出未选入的条目数量和估算体量。使用方必须知道信息不完整，否则只能在全部重读和直接采信之间二选一。

各角色的可见内容：

| | plan.yaml | 任务卡 | 账本目录 | excluded | 源码片段 | unverified 结论 |
|---|---|---|---|---|---|---|
| 规划 | 全量 | 全量 | 目录 + 按需 | 全量 | 按需 | 全量 |
| 执行 | 全量 | 仅自己的卡 | 目录 + 按需 | 全量 | 按需 | 全量 |
| 审查 | 不提供 | 不提供 | 不提供 | 不提供 | 变更文件前后全文 | 不提供 |

## Handoff 契约（L3）

- handoff 是否写、何时写由执行方决定——推荐写入（闭合纠错回路、向下游传递失效），但绝非义务；没有 handoff 的 dossier 不是缺陷。写入时文件名按任务卡序号（`01_to_02.md`）。
- Actual Outputs、Deviations、State Snapshot 三段齐全，缺任一段即不是合法 handoff。三段结构与示例见 [schema.md](schema.md)。
- 存在 handoff 时，同一节点以最新一份为准；它既是偏离的记录通道，也是向下游传递"哪些账本条目已过期"的载体。

## 执行阶段

执行行为属于执行方自己的工作流，本规范不做任何规定。工件提供的是：

- plan.yaml、账本目录与所属任务卡让执行方无需重新检索即可获得结论、排除项和精确定位；其他任务卡不在其 packet 内（靠组装隔离，不靠规则禁止）。
- 账本 locator 是指针不是内容：cites 的消费方式就是读取目标片段。哈希不匹配的条目不足以作为编辑依据。
- `excluded` 与冻结的任务卡让偏离可检测：越界修改或违背冻结步骤即计划失效事件；执行方回写 handoff 时，Deviations 是其记录通道。
- `trust: checked` 的 assertion 可重放，任何结论都能以一条命令的成本重新验证。

## 审查阶段

review.packet.md 在交接时编译（见 views/），隔离是其内容的属性，不是加给审查方的规则。审查方如何工作是其自己的流程。

## 失效处理

每级失效的含义，以及工件为其提供的支持：

| 级别 | 含义 | 工件支持 |
|---|---|---|
| 位置失效 | 被引用文件被删除或移动——条目按定义即作废 | 重新检索的结果记录为新条目 |
| 内容失效 | region_sha 不匹配，或目视内容与 intent 不符 | 修订记录为带 `supersedes` 的新条目（若记录）；回写 handoff 时由 State Snapshot 向下游传递，未回写则该条目在重新验证前按 unverified 对待 |
| 上下文失效 | 内容未变但调用方或依赖已变，或条目声明的 `invalidation` 条件已成立 | 有 assertion 时，重放一条命令即可重新验证；没有则该结论在重新验证前按 unverified 对待 |

- 文件变化只影响指向它的条目，计划与账本的其余部分仍然有效。局部失效或局部计划失效事件不作废整份计划。
- 执行方何时、如何执行这些检查是其自己的工作流；工件的职责是让每次检查便宜、结果可记录。第三级失效没有低成本的通用检测手段——assertion 与声明的 `invalidation` 条件是部分答案。
